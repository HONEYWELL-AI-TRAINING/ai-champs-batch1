PR Automation
Automate the routine parts of PR review — let humans focus on design
PR automation = faster reviews, fewer defects. Automated checks run on every PR: linting, test coverage, style compliance, security scanning. Only design-level issues reach human reviewers. This is how you scale review quality across a team.
🚀
What PR Automation Covers
✅
Static Analysis
Linting, formatting, complexity analysis, dead code detection. Catches style and structural issues automatically.
📊
Test Verification
Verify tests pass, check coverage thresholds, validate test-to-spec mapping. Every PR must have test evidence.
🛡
Security Scanning
SAST, dependency scanning, secret detection. Catch vulnerabilities before code is merged.
🔄
Automated PR Workflow
1. Developer pushes code
PR is created (manually or via MCP workflow from Module 07). Automated checks trigger immediately.
2. Static analysis runs
Linting, formatting, complexity checks. Results posted as PR comments. Pass/fail gates enforced.
3. Tests execute
Full test suite runs. Coverage report generated. Regression check against baseline.
4. LLM-as-Judge reviews
AI reviews the diff for design patterns, non-functional criteria, and spec compliance. Results posted.
5. Human reviews design
Human reviewer sees all automated results and focuses on architecture, design decisions, and edge cases.

LLM-as-Judge
Using AI to review AI-generated code — scalable, consistent, tireless
LLM-as-Judge = AI reviewing AI. A separate LLM reviews the code diff against defined criteria: coding standards, design patterns, spec compliance, non-functional requirements. It provides structured feedback that human reviewers can act on.
🤖
How LLM-as-Judge Works
// LLM-as-Judge Review Prompt INPUT: diff = the code changes in this PR spec = the specification for this feature standards = coding standards for the project nfr = non-functional requirements checklist TASK: Review the diff against each criterion: 1. Does the code match the spec? 2. Does it follow coding standards? 3. Are non-functional criteria met? 4. Are there any defect patterns? 5. Is test coverage adequate? OUTPUT: score per criterion (PASS/WARN/FAIL) explanation for each result recommendations for improvements

🔍
Review Criteria Categories
Coding Standards ▼
Naming conventions, formatting, comment style, header guards, file organization. Catches style drift that linters can't fully enforce. Ensures consistency across AI-generated and human-written code.
Design Patterns ▼
Correct use of design patterns, appropriate abstraction levels, proper error handling patterns, state machine correctness. The LLM can compare the code against known good patterns for the domain.
Spec Compliance ▼
Verify the implementation matches the specification from Module 04. Check that all acceptance criteria are addressed, interfaces match the spec, and behavior aligns with requirements.
Defect Patterns ▼
Common embedded defects: buffer overflows, null pointer dereferences, race conditions, resource leaks, incorrect timeout handling, missing bounds checks. Pattern-based detection catches known bug classes.
Quality Gates
Define, enforce, and measure — every PR must pass before merge
Quality gates = non-negotiable standards. Every PR must pass defined quality gates before merge. No exceptions, no overrides without approval. This is how you maintain consistent quality across a team, even when AI generates the code.
🛡

📈
Gate Enforcement Levels
🚫
Block
PR cannot merge. Build errors, test failures, critical security issues. Must be fixed before any progress.
⚠
Warn
PR can merge with approval. Coverage below threshold, non-critical lint warnings. Requires tech lead sign-off.
✅
Info
PR can merge freely. Suggestions, best practices, documentation improvements. Informational only.

Non-Functional Criteria
The criteria that separate working code from production-ready code
Non-functional criteria (NFRs) are the requirements that don't describe what the code does, but how it does it: performance, memory usage, security, maintainability, reliability. These are the hardest to verify automatically — and the most important for embedded systems.
📋
NFR Checklist for Embedded Systems
NFR CategoryCriteriaVerification Method
Performance Worst-case execution time within budget Profiling + static analysis
Memory Stack/heap usage within limits, no leaks Static analysis + runtime tools
Security No buffer overflows, no injection, no secrets in code SAST + secret scanning
Reliability Error handling, graceful degradation, watchdog compliance LLM-as-Judge + code review
Maintainability Low complexity, clear naming, adequate comments Static analysis + LLM-as-Judge
Portability No platform-specific code without guards LLM-as-Judge + build matrix
Testability Functions are testable in isolation, no global state LLM-as-Judge + coverage analysis

LLM-as-Judge NFR Review
The LLM reviews each NFR category against the code diff. For each criterion, it provides a PASS/WARN/FAIL rating with explanation.
// Example NFR review output Performance: PASS — No loops with unbounded iteration Memory: WARN — Large stack allocation in sensor_poll_all() Security: PASS — No buffer operations without bounds checking Reliability: FAIL — Missing error handling for UART timeout Maintainability: PASS — Functions under 50 lines, clear naming Portability: PASS — Platform code properly guarded Testability: PASS — All functions have corresponding test cases // RESULT: 1 FAIL, 1 WARN — requires fixes before merge

Best Practices for NFR Enforcement
Start with the Cohort's Consensus ▼
The cohort identified memory usage, design pattern conformance, and timing constraints as the NFRs most commonly missed in review. Start with these three — they're the highest-value gates.
Iterate on Criteria ▼
Start with a small set of NFRs and expand over time. Each false positive is a tuning opportunity. The goal is high signal-to-noise, not maximum coverage on day one.
Combine Automated + LLM ▼
Use static analysis for measurable criteria (memory, complexity). Use LLM-as-Judge for subjective criteria (design patterns, maintainability). Each tool covers the other's blind spots.
Feed Back into Specs ▼
When LLM-as-Judge finds a NFR violation, update the specification to include that NFR as an acceptance criterion. This closes the loop: NFRs become part of the spec, which triggers tests, which are verified by quality gates.
Self-Check Quiz
Verify your understanding of Module 09 key concepts

Q1. What is the primary role of LLM-as-Judge in the PR review process?

A Replace human reviewers entirely
B Review code against defined criteria, freeing humans for design review
C Generate the code that needs reviewing
D Write test cases for the PR
Correct! LLM-as-Judge reviews code against defined criteria (standards, NFRs, spec compliance) and provides structured feedback. It handles the routine checks so human reviewers can focus on design, architecture, and edge cases.

Q2. Which quality gate action means "PR can merge with approval"?

A Block
B Warn
C Info
D Pass
Correct! Quality gates have three levels: Block (cannot merge), Warn (can merge with tech lead approval), and Info (can merge freely). Warn is used for non-critical issues like coverage below threshold or non-critical lint warnings.

Q3. What are non-functional criteria (NFRs)?

A Requirements that describe what the code does
B Requirements for code formatting and naming
C Requirements about how the code performs (performance, security, memory)
D Requirements for test coverage
Correct! NFRs describe how the code performs rather than what it does: performance (execution time), memory usage, security, reliability, maintainability, and portability. These are critical for embedded systems and hardest to verify automatically.

Q4. In the automated PR workflow, what runs immediately after the developer pushes code?

A Static analysis (linting, formatting, complexity checks)
B Human code review
C Deployment to production
D LLM-as-Judge review
Correct! When a PR is created, automated checks trigger immediately. The first stage is static analysis: linting, formatting, complexity checks. Results are posted as PR comments and gates are enforced. LLM-as-Judge runs later in the pipeline.

Q5. Why should LLM-as-Judge not replace human reviewers?

A LLMs are too slow for code review
B LLMs cannot read code diffs
C LLMs lack business context and cannot make design decisions
D LLMs are too expensive for code review
Correct! LLM-as-Judge excels at pattern-based checks (standards, NFRs, defect patterns) but cannot understand business context, make design trade-off decisions, or evaluate architectural fitness. Human reviewers are essential for these judgment calls.
